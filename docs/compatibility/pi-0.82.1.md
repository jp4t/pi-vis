# Pi 0.80.10 → 0.82.1 compatibility audit

Audited against the upstream coding-agent changelog and public package surface from `v0.80.10` through `v0.82.1` on 2026-07-25. Production Pi-Vis bundles and runs exactly `@earendil-works/pi-coding-agent@0.82.1` (see `src/main/pi/pinned-pi.ts`); it never detects or runs a user-installed Pi. Tests use that same repository-local package. Changing the pin is a Pi-Vis release decision and requires repeating this audit.

## Integration-significant handling

| Upstream change | Pi-Vis handling |
|---|---|
| Summarization retry lifecycle (`summarization_retry_scheduled`, `summarization_retry_attempt_start`, `summarization_retry_finished`) | The typed event contract recognizes all three events. State authority projects retry wait/attempt transitions onto the existing compaction or navigation operation, keeps compaction/navigation custody fenced during backoff, and waits for the surrounding operation's own terminal evidence before draining. |
| Tool, compaction, and branch-summary usage accounting | The shared usage schema preserves Pi's public usage/cost value on live tool results, persisted tool messages, compaction results/entries, and branch-summary entries. History hydration and the transcript reducer keep it on the corresponding block. The context meter refreshes after turns, compaction, and a completed navigation that persisted a branch summary, plus its safety poll. |
| Public `AgentSession.getAvailableThinkingLevels()` | Each direct authority snapshot calls the public method when present and projects the result. The thinking picker uses that authoritative list; its model-capability calculation remains only a compatibility/presentation fallback. |
| Public `ExtensionRunner.emitInput()` result | The SDK bridge observes the final `continue` / `transform` / `handled` result once under the owning prompt's admission context. An unchanged `continue` preserves exact queued-steer identity and deletion even when passive input hooks are installed; transformed, handled, nested, and handler-side-effect queue work remains unowned. |
| Messages queued during compaction retain their requested lane | Pi owns this fix internally. Pi-Vis continues to submit through public prompt/queue APIs and never rewrites Pi's selected steering/follow-up lane. |
| Native provider extensions and provider lifecycle types | `createAgentSessionServices()` discovers and registers native provider extensions before Pi-Vis creates the session. Pi-Vis uses only the returned public `ModelRuntime`; it does not copy or narrow provider definitions, so provider-specific auth, model transformation, streaming, and constrained-sampling capability metadata flow through unchanged. |
| Qwen token providers, OpenRouter/Kimi interactive auth, Anthropic bearer auth, provider/model catalog updates, and ETag refresh | These are implemented by the pinned public `ModelRuntime` and bundled `pi-ai`. Pi-Vis's owner-bound login and refresh intents call that runtime directly. Model pickers perform silent stale-while-revalidate refresh on open and after auth changes. Credentials and provider errors never enter authority outcomes. |
| Public diagnostic model-scope resolution and unavailable configured patterns | Every saved-pattern, picker-initialization, model-dropdown, and live-scope path calls Pi's public `resolveModelScopeWithDiagnostics()`. Pi therefore owns exact/partial/name/glob matching, colon-bearing IDs, thinking suffixes, canonical order, and deduplication. Only `no-match` diagnostics become removable `Unavailable` rows; an `invalid-thinking-level` warning that still resolves a model does not create a false stale row. An unavailable pattern does not make “all available models” a restrictive live session scope, while persistence still retains the stale pattern. |
| Constrained tool sampling | Pi-Vis does not wrap or reconstruct extension tool definitions. `Tool.constrainedSampling` and provider capability flags therefore pass from public extension/provider registration into the pinned agent core unchanged. |
| Direct bash streaming and correlated `bash_execution_update` | `runBash` and the compatibility `bash` command pass their stable request/intent ID to public `AgentSession.executeBash()`. The child brackets Pi's correlated update events with Pi-Vis-owned start/end transcript events, producing one live Composer-bound terminal surface, one normalized settled Shell Turn, and one terminal operation outcome. `!!` preserves `excludeFromContext`. |
| Bash session/model environment variables | Built-in agent bash tools are created by Pi's public SDK factory, so `PI_SESSION_ID`, `PI_SESSION_FILE`, `PI_PROVIDER`, `PI_MODEL`, and `PI_REASONING_LEVEL` are supplied by the pinned runtime. Pi-Vis does not replace the built-in bash tool or import private Pi internals. |
| `MessageRenderOptions.outputPad` | Custom-message rendering passes the public settings manager's current output padding to the registered message renderer. Entry renderers retain their distinct `EntryRenderOptions` contract. |
| Local llama.cpp model management | Upstream installs this as a hidden CLI-main built-in and does not export its factory from the public SDK entry. [ADR 0006](../decisions/0006-pinned-llama-private-extension-exception.md) approves one exact-version adapter: it derives the shipped `dist/extensions/index.js`, selects only the hidden `llama.cpp` factory, validates its shape, and injects it through public `resourceLoaderOptions.extensionFactories`. `/llama`, `/login llama.cpp`, router catalog/load/unload/download/retry behavior, the native provider, and Pi-TUI custom panel then run unchanged from Pi 0.82.1. |
| Remaining provider/core fixes | Fallback streaming, custom OpenAI-compatible tools, Google/Anthropic header and reasoning fixes, model catalog changes, scoped API-key visibility, and llama catalog persistence are owned by the pinned `pi-ai`/coding-agent runtime and require no Pi-Vis protocol adaptation. |

The earlier SDK-host integrations remain in force: `agent_settled`, custom entry/message rendering, extension command errors, cache-miss notices, optional session names, `ThinkingLevel.max`, zero-message model/thinking restoration, confined runtime aliases, prompt preflight fencing, project trust, and the public `ModelRuntime` adapter. The host's 0.80.6–0.80.7 public-surface adapter paths remain testable but are unreachable in production while the exact pin is 0.82.1.

## Authority compatibility

Pi 0.82.1 supplies the public getters and methods the host snapshots directly: streaming/idle/compaction/retry/bash state, model/session metadata, available thinking levels, pending queues, prompt preflight, queue clearing, navigation, abort primitives, and the canonical model/auth runtime. Snapshot identity, epoch, sequence, leases, submission custody, editor revisions, and queue restoration remain Pi-Vis protocol features around those public APIs.

Compaction still clears its getter immediately after the synchronous terminal callback, so the host retains its conservative microtask reconciliation barrier. Summarization backoff is part of the same observed compaction/navigation span rather than a synthetic terminal operation. A compact invocation drains custody only after both public lifecycle/getter reconciliation and the public `compact()` promise settle.

## Regression gates

`tests/pinned-pi-runtime.test.mts` gates the manifest pin, installed coding-agent/core/AI package versions, executable layout, and the 0.81–0.82 public declarations and runtime exports Pi-Vis consumes. `pinned-pi-private.test.mjs` and `host-imports.test.ts` gate the one private llama registry path, exact version and entry shape, and prohibit any second private host dependency. Host, protocol, reducer, history, picker, and renderer tests cover retry projection, usage preservation, public thinking constraints, Pi-owned model-scope diagnostics, unavailable scopes, correlated bash streaming, and `outputPad`.

The real SDK suites (`tests/e2e/real-sdk-host-smoke.spec.mts`, `real-sdk-transcript-lifecycle.spec.mts`, `real-sdk-regressions.spec.mts`, `real-sdk-races.spec.mts`, `authority-faults.spec.mts`, and `llama-manager.spec.mts`) run the exact local 0.82.1 executable in isolated directories with loopback providers where model work is needed. The llama gate configures a fake router through the production `settings.piEnv` path, renders the real manager panel, closes it through the panel-input Escape path, and selects its synchronized native-provider model. Run `npm run test:e2e:real-pi` for that focused gate or `npm run test:full` for the release gate.
